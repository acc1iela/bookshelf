## Phase 1: API設計（2026-11-18）

- **わからない点を残したまま承認しない** — 「〜だっけ？」と書いた直後に「気になる点はない」で通すと、それが雑なレビューになる。疑問は質問するか、自分で調べて解消してから承認する。
- **用語の前提を揃える** — 「バージョニング」を読書の進捗のことだと誤解したまま、結論だけ合っていた。理由が間違っていると、前提が変わったときに判断を誤る。
- **nullable なカラムの `ORDER BY` は NULL の位置を確認する** — NULL の並び順は DB ごとに違う（PostgreSQL は `DESC` で先頭、SQLite/MySQL は末尾）。必要なら `COALESCE` や `NULLS LAST` を使う。
- **DB の形と API の形は分けて考える** — テーブル構造をそのままレスポンスに流していると、DB を変えたときにクライアントが壊れる。
- **「問題ない」と言う前に実害を数える** — 二重送信のような「問題ない」は、集計値の水増しのような副作用を見落としていることが多い。対策の置き場所（サーバー or クライアント）は、要件で決める。
